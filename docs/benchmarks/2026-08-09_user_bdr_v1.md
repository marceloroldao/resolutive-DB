## Purpose

Preserve and evaluate the user-provided BDR implementation as an independent baseline before modifying the algorithm. The objective is to distinguish measured behavior from theoretical claims.

## Environment used for this run

- Python: 3.13.5
- Compiler: GCC 14.2.0
- OS: Linux 6.18.35 x86_64, glibc 2.41
- `PYTHONHASHSEED`: not set in the executing process
- Query count per N: 500
- Dataset sizes: 10,000; 50,000; 200,000; 1,000,000
- Key pattern: `USER_KEY_RESOLUTIVE_%08d`
- BDR address space: `max(2*N, 100_000)`

## Important reproducibility warning

The baseline uses Python's built-in `hash(str)`. Python intentionally randomizes string hashing between interpreter processes unless `PYTHONHASHSEED` is fixed. Therefore the exact bucket layout, collision distribution, and timings are not bit-for-bit reproducible across separate runs by default.

For controlled reproduction, execute with a fixed seed, for example:

```bash
PYTHONHASHSEED=0 python benchmarks/baselines/user_bdr_v1_as_received.py
```

The future corrected benchmark should replace built-in `hash()` with a deterministic encoder or record `PYTHONHASHSEED` explicitly.

## What the result shows

The observed BDR lookup latency remained approximately flat over the tested N range. In this run it stayed around 1.3–1.6 us/query while binary search increased from roughly 0.41 us to 1.83 us. Python `dict` remained substantially faster in absolute latency.

However, the benchmark grows `space_size` approximately proportionally to N (`space_size = 2*N` after 50,000 records). Therefore the load factor is intentionally held near 0.5 rather than allowing density to rise. The flat curve is compatible with expected constant average bucket occupancy under proportional memory growth.

This is a valid architecture test, but it is not yet evidence that lookup remains O(1) when memory is fixed or when collision density increases.

## Complexity analysis of this implementation

The first-stage bucket lookup is direct array addressing and is O(1).

The second stage is:

```python
for ent in cesto:
    if abs(ent.phi - target_phi) < 1e-7 and ent.key_id == key_id:
        return ent
```

Therefore lookup cost is actually O(k), where `k` is the number of entities in the selected bucket. If expected bucket occupancy is bounded by maintaining `space_size = Theta(N)`, expected lookup can remain O(1). Worst-case lookup is O(N) if all keys map to one bucket.

Accordingly, this V1 implementation should be described as **expected O(1) under bounded bucket occupancy**, not unconditional worst-case O(1).

## Fidelity test interpretation

The original fidelity test inserts one known key and verifies one exact payload. Passing it demonstrates basic exact-key recovery for that item, but it does not establish 100% fidelity over the dataset or under collisions.

A stronger fidelity suite should verify every inserted key or a deterministic large sample, include misses, duplicate updates, forced bucket collisions, forced phase collisions, deletion, and process restart/persistence where applicable.

## Engineering findings

1. `hash(str)` is process-randomized and should not be the canonical BDR address encoder for a reproducible database.
2. `phi` is derived from the same 32-bit `h` as `rho_R`; it is therefore not an independent discriminator.
3. Floating-point phase comparison with tolerance `1e-7` is unnecessary for an address index and can introduce equivalence ambiguity. Quantized integer phase signatures are more reproducible.
4. The bucket is a Python list and requires a scan. A second direct/indexed phase level would remove most list scans in the normal case.
5. `space_size = 2*N` gives useful constant-load behavior but consumes O(N) bucket-pointer memory. Memory per stored record must be measured alongside latency.
6. Insertion always appends, so duplicate keys produce duplicate entities and increase `count`; update semantics are undefined.
7. The benchmark labels the sorted-list binary search as a tree baseline, but it is not a B-tree database implementation. It should be called `sorted list + bisect` and actual SQLite/PostgreSQL B-tree tests should be separate.
8. Five hundred queries are too few for robust sub-microsecond comparisons. Future tests should use warm-up, thousands to millions of queries, repeated rounds, medians/percentiles, and process-level repetitions.

## Required next tests

- Fixed address-space test: hold `space_size` constant while N rises.
- Load-factor sweep: 0.25, 0.5, 0.75, 1, 2, 4, 8+ records per bucket on average.
- Hit versus miss latency.
- Adversarial/forced collision test.
- Full fidelity verification.
- Duplicate/update/remove semantics.
- Memory usage per record and total RSS.
- Comparison against Python dict, SQLite indexed lookup, DuckDB, Redis, and later PostgreSQL.
- Comparison of V1 built-in hash encoder against deterministic BDR encoder.

## Current technical verdict

The code is a useful and compact baseline demonstrating direct density-bucket addressing. The observed scaling is encouraging for expected lookup latency when memory grows with N. It does **not yet prove a novel worst-case O(1) database engine**, because bucket resolution remains linear in bucket occupancy and Python's hash table remains faster in absolute lookup latency.

The most promising next engineering step is to preserve the direct `rho_R` layer while replacing list scanning with a deterministic, quantized phase index and then stress that structure at increasing fixed density. That experiment will show whether the phase coordinate contributes genuine collision-resolution value beyond an ordinary two-level hash/index design.
