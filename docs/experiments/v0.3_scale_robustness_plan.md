# BDR v0.3 — Scale and Robustness Validation Plan

Status: Experimental. This branch does not change the published v0.2.0-rc1 release.

## Objective

Determine whether the consolidated BDR engine remains correct, durable and operationally predictable as dataset size, operation count, concurrency and repeated failure increase.

This phase prioritizes attempts to break the engine over adding new features.

## Baseline

- Published line: v0.2.0-rc1
- C ABI: v1 (frozen for the v0.2 RC line)
- Persistent formats: BDR3 snapshots / BDW3 WAL
- Existing evidence: V100 candidate=true; 500,000-mutation soak passed.

## Test ladder

Scale tests must advance progressively and stop on the first unexplained divergence.

1. 1,000,000 mutations
2. 5,000,000 mutations
3. 10,000,000 mutations
4. 25,000,000 mutations
5. 50,000,000 mutations

A larger tier is attempted only after the previous tier is reproducible.

## Required workloads

- uniform random keys
- sequential keys
- UUID-like keys
- common-prefix strings
- Zipf/skewed access
- hot keys / hot partitions
- mixed PUT/GET/DELETE
- checkpoint-heavy workload
- reopen-heavy workload
- repeated crash/recovery workload

## Concurrency

At minimum test 1, 4, 8 and 16 writers where the API contract permits it.

Record throughput, durable-confirmation latency, p50/p95/p99, errors, final-state equality and recovery time.

## Correctness oracle

Every durability/recovery experiment must compare the reopened BDR state against an independent reference state. Throughput alone is never a PASS condition.

Required invariants include:

- final-state equality
- no acknowledged durable write lost
- monotonic sequence behavior
- last_sequence == durable_sequence after required synchronization/recovery boundaries
- deleted keys remain absent
- values remain byte-exact

## Failure injection

Test repeated process termination at varied points around:

- WAL append
- WAL synchronization
- checkpoint creation
- checkpoint rename/commit
- WAL retirement
- reopen/recovery

Corruption tests must distinguish expected conservative truncation/rejection from silent state divergence.

## Resource pressure

Where CI/host capabilities permit, record:

- peak RSS
- database bytes on disk
- WAL bytes
- checkpoint bytes
- bytes per live record
- recovery time
- CPU time

Add constrained-memory tests only with explicit reproducible limits.

## Market comparison

Continue comparison with SQLite, LMDB, LevelDB and RocksDB when contracts can be made meaningfully comparable.

Do not claim universal superiority. Preserve negative results. Separate synchronous per-operation durability from grouped/batched durability.

## Acceptance criteria

A tier passes only if:

1. no oracle divergence occurs;
2. no acknowledged durable write is lost;
3. recovery remains deterministic;
4. no unexplained crash/deadlock occurs;
5. results and parameters are persisted as machine-readable artifacts.

Performance regression is recorded, not hidden. A performance regression alone is not a correctness failure unless it violates an explicitly defined operational bound.

## v0.3 exit criteria

The v0.3 robustness phase is considered complete only after:

- at least 10 million mixed mutations pass reproducibly;
- repeated crash/recovery campaign passes;
- 1/4/8/16-writer tests complete without state divergence;
- large reopen/checkpoint campaign passes;
- resource-growth behavior is documented;
- market benchmarks are rerun with equivalent durability contracts;
- all failures and negative results are documented.

Only after these gates should BDR integration with Memoria.ia be promoted from compatibility experiment to a sustained real-workload validation target.
