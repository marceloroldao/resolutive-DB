# BDR v0.3 — Scale and Robustness Results

Status: experimental branch `experiment/v0.3-scale-robustness`.

This report consolidates the reproducible evidence gathered after the published v0.2.0-rc1 line. It does not modify historical v0.2 release evidence.

## Summary

The consolidated V86 core passed the planned scale ladder from 1 million to 50 million mixed operations with deterministic seed, independent in-memory oracle, periodic sync, checkpoint, reopen, final-state verification, and sequence consistency checks.

It also passed dedicated 1/4/8/16-writer concurrency scenarios and 50 repeated SIGKILL/recovery cycles without losing writes that had been externally recorded as durable.

These results support robustness claims for the tested workloads only. They do not establish universal production readiness, universal superiority over other engines, or strict worst-case O(1) behavior.

### Scale interpretation

Within this workload, peak RSS grew from about 50 MB at 1M operations to about 56 MB at 25M/50M and then remained approximately flat because the live key-space was bounded to 100,000 keys. This is not evidence that memory usage is independent of database cardinality. A future test must grow the key space and number of live records proportionally with operation count.

Wall time increased approximately with work performed under the repeated sync/reopen/checkpoint regime. No state divergence was observed.

### Concurrency interpretation

Correctness passed for all tested writer counts. The 8-writer throughput result is an obvious non-monotonic outlier and must not be interpreted as a stable scalability curve. GitHub-hosted runners can vary in scheduling and shared-host conditions. The concurrency benchmark should therefore be repeated multiple times per writer count and reported using median/p95 before performance conclusions are made.

## Crash/recovery gate

A dedicated process-level gate executed 50 rounds with varied SIGKILL timing. A manifest external to the database recorded only writes already considered durable. After each kill, the database was reopened and every manifest entry was verified.

Result:

`V03_CRASH PASS rounds=50 durable_manifest_keys=100`

No externally recorded durable write was lost.

Artifact SHA-256: `64e0d620c585df100ed4f8c4399532dafbabbfa0470eeb9d90acfad4ebd35c3f`.

This validates the tested crash positions and durability contract. It is not a proof against every possible storage, kernel, filesystem, power-loss, or hardware failure mode.

## Exit criteria status

- at least 10 million mixed mutations pass reproducibly: **PASS**; extended to 50 million;
- repeated crash/recovery campaign: **PASS** (50 SIGKILL cycles);
- 1/4/8/16 writer validation without state divergence: **PASS**;
- large reopen/checkpoint campaign: **PASS** through 5,000 cycles at 50M operations;
- resource-growth behavior documented: **PARTIAL**; bounded-key-space results documented, cardinality-scaling test still required;
- equivalent-contract market benchmarks rerun: **PENDING for the v0.3 scale workload**;
- negative/anomalous results documented: **PASS** (8-writer throughput outlier retained).

## Important scope note on V99/V100

V99/V100 were release-candidate evidence-closure workflows created for the v0.2 line. Failures of those historical metadata/staging workflows on the v0.3 experimental branch are not v0.3 scale/correctness failures and should not be used as v0.3 gates. The relevant v0.3 gates are BDR CI, V0.3 Scale Gate, and V0.3 Concurrency and Crash Gates.

## Remaining work before declaring v0.3 validation complete

1. Grow live cardinality, not only mutation count: e.g. 100k → 1M → 5M+ simultaneously live records.
2. Measure database, WAL and checkpoint bytes per live record at each cardinality.
3. Repeat concurrency scenarios multiple times and report median/p95/p99 rather than one sample.
4. Run equivalent durability-contract comparisons against SQLite, LMDB, LevelDB and RocksDB under the same datasets and host assumptions.
5. Add Zipf/hot-partition and common-prefix workloads using the consolidated V86 core.
6. Extend crash injection around checkpoint creation/rename and WAL retirement boundaries.

## Current conclusion

For the tested bounded-key-space workload, BDR's consolidated core remained correct through 50 million mixed operations, 5,000 reopen/checkpoint cycles, 1/4/8/16-writer correctness tests and 50 SIGKILL/recovery cycles. This is a meaningful robustness milestone.

The next highest-value question is no longer whether the engine survives more repetitions of the same bounded workload. It is whether behavior remains controlled as the number of simultaneously live records, database size, skew and external-engine comparisons increase.
