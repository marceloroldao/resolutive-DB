# BDR v0.3 — Cardinality Growth Results

Status: experimental evidence on `experiment/v0.3-scale-robustness`.

## Purpose

The earlier 1M→50M mutation ladder reused a 100,000-key space. That validated repeated mutation, reopen and checkpoint behavior, but it did not establish memory or storage growth with increasing numbers of simultaneously live records.

This experiment therefore measures 100,000, 1,000,000 and 5,000,000 live records using the consolidated V86 engine.

## Interpretation

### Persistent storage growth

Disk usage is close to linear over the tested range, rising from approximately 115.8 to 119.6 bytes per live record. This is encouraging for persistent-size predictability, but the number is workload-specific because key/value sizes are fixed by the gate.

### Memory growth

Peak RSS grows substantially with live cardinality:

- ~65 MiB at 100k records;
- ~560 MiB at 1M records;
- ~3.00 GiB at 5M records.

This is roughly on the order of 0.6 KiB of process RSS per live record at the larger tiers. RSS includes allocator, engine, test process and temporary recovery/checkpoint costs, so it is not a pure per-record structure-size measurement. Still, it identifies RAM footprint as a current scaling constraint that deserves optimization before production-scale claims.

### Lookup

Verified lookup throughput fell from ~4.16M lookups/s at 100k to ~1.63M at 1M, then remained around ~1.61M at 5M. This suggests a cardinality-sensitive transition followed by a relatively stable regime in this workload, but more repetitions and latency percentiles are required before drawing a strong conclusion.

### Insert anomaly

The 100k tier reported much lower insert throughput than the 1M tier. This is not interpreted as a real super-linear speedup. Fixed startup/preallocation/synchronization costs and hosted-runner variability can dominate a short 100k run. Future comparisons must use repetitions, warm-up and median/p95 statistics.

## Current conclusion

The V86 engine demonstrated correctness through 5 million simultaneously live records in the tested GitHub Actions environment. Persistent bytes per record remained nearly linear, while RAM usage grew to approximately 3 GiB at 5 million records. The primary scaling optimization target revealed by this experiment is therefore in-memory representation/index overhead, not persistent-file growth.
